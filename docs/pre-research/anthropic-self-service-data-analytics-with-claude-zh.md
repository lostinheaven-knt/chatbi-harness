许多数据科学和数据工程团队都有同感：要真正实现自助式业务分析，过去往往是一项旷日持久的苦差事。

一种常见做法，是用宽表和反规范化表，让不太懂技术的同事更容易访问数据模型。但随着业务扩张，这通常会产生大量相互重叠、定义却不一致的视图；对于根本不想学习 SQL 的员工，它也并没有真正弥合使用门槛。另一种做法，是为用户建立边界更清晰、彼此隔离的分析环境，但这又容易遗漏大量长尾业务问题。各团队在孤岛中各自建设，最终造成指标和仪表盘不断膨胀。

大语言模型的兴起，为自助式分析提供了第三条道路，有机会绕开这些问题。不过，如果只是让 Claude 连接数据仓库，再放手让智能体执行查询，就很容易制造一种“答案十分精确”的错觉。

一开始，数据团队可能会为摆脱临时分析请求而欣喜；很快却会意识到，这种设置把业务相关方与底层基础设施、文档和专业知识隔离开来，而这些因素过去恰恰会引导他们使用经过精心治理的数据集。喜悦于是变成担忧。

在 Anthropic，95% 的业务分析查询已经通过 Claude 自动完成，整体准确率约为 95%。把这些往往机械、重复的工作交给 Claude 后，数据科学团队便能把精力投入因果建模、预测和机器学习等更具战略价值的工作。

Anthropic 团队与数十位最熟练的 Claude Code 用户交流，并观察了大量分析智能体的设计模式，由此总结出一组适用于其他 LLM 数据团队的最佳实践。本文将介绍如何最大化 Claude 生成自助式业务洞察的能力，包括：

- 为什么分析准确率本质上是上下文与验证问题，而不是代码生成问题；
- 导致大多数错误的三种失败模式；
- Anthropic 为解决这些错误而构建的智能体分析技术栈；
- 如何衡量系统的有效性；
- Anthropic 大多数 Skill 所采用的基础模板（见附录）。

## 数据不是软件

LLM 的生成能力是一把双刃剑：让模型能够创造性地解决复杂问题的机制，同样也可能生成幻觉和错误结果。要充分理解分析智能体面临的挑战，可以先把它与编码智能体进行比较。

编码面对的是开放式解空间，模型的创造力往往会得到奖励；与此同时，文档和测试还会形成天然护栏，帮助发现幻觉。数据分析则不同：一个问题通常只有一个正确答案，往往还必须来自唯一正确的数据源，但我们并没有一种确定性方法可以证明结果一定正确。

| 处理阶段 | 编码 | 数据分析 |
| --- | --- | --- |
| **上下文** | 代码库通常维护得较好。README、类型签名、文档字符串和提交历史会在编写代码前为智能体提供丰富、结构化的上下文。 | 数据库可能包含数百万个字段，其中很多文档并不完整；仅“收入”就可能出现在数千处。即使找到了正确字段，不同团队也可能用不同方式定义同一指标，两个答案可能在技术上都正确，却只有一个适合当前业务场景。 |
| **生成** | 到真正编写代码时，智能体可以选择多种正确实现，因此一个看起来合理的答案通常也是有效答案。 | 分析方案的实现往往很简单，例如 5-10 行 SQL 或 Python，但通常只有一种正确方法。 |
| **验证** | 对代码而言，编译器、Linter 和单元测试能快速提供确定性反馈。 | 分析没有编译器、单元测试或天然的标准答案。除非预先定义期望、用其他来源交叉验证或与历史基线比较，否则无法用确定性方法确认结果正确。 |

对于面向业务的自助式智能体分析，复杂性主要来自数据的歧义。核心问题可以归结为：**我们能否把用户的问题映射到数据模型中具体、最新的实体，并知道使用这些实体的正确方式。** 一旦做到了这一点，后续执行和 SQL 编写其实就很简单。

Anthropic 识别出三个关键因素，它们造成了绝大多数不准确的回答：

1. **概念与实体之间的歧义（concept <> entity ambiguity）**：一个数据模型中可能有数百个看似可用的选项，背后甚至涉及数百万个字段，智能体无法选择最适合回答问题的字段。例如，衡量“活跃用户数”时，什么行为才算“活跃”？是否应排除欺诈用户？回溯窗口应该多长？
2. **数据陈旧（data staleness）**：数据源、业务定义和 Schema 一直在变化；数据资产和智能体知识会逐渐过期，继而返回不易察觉却实际错误的答案。
3. **检索失败（retrieval failure）**：正确的信息可能确实存在于数据模型中，也得到了适当标注，但搜索空间太大，智能体就是找不到它。

## Anthropic 的智能体分析技术栈

Anthropic 主要通过一套智能体数据栈来降低上述三类错误。每一层都重点解决其中一个或多个问题：

1. **实体歧义**：数据基础和事实来源不断缩小候选实体空间，直到只剩一个经过治理的答案。
2. **陈旧问题**：维护和验证流程使数据及知识能够跟随业务变化，避免逐渐腐化。
3. **检索失败**：Skills 确保智能体能够稳定找到并正确使用这个答案。

```text
┌─ 01 数据基础
│  ├─ 组成：数据模型 · 转换 · 测试 · 元数据
│  └─ 解决：实体歧义、数据陈旧
│
└────────────── 建立受治理的数据底座
                       │
                       ▼
┌─ 02 事实来源
│  ├─ 组成：语义层 · 数据血缘 · 查询语料 · 业务上下文
│  └─ 解决：实体歧义
│
└────────────── 将业务概念映射到唯一实体
                       │
                       ▼
┌─ 03 Skills
│  ├─ 组成：知识路由 · 操作手册 · 参考文档
│  └─ 解决：检索失败、数据陈旧
│
└────────────── 规定如何查找并使用实体
                       │
                       ▼
┌─ 04 验证
│  ├─ 组成：离线评测 · 消融实验 · 在线监控
│  └─ 检查：实体歧义、数据陈旧、检索失败
│
└────────────── 发现问题并反馈到前面各层
```

沿箭头从上往下看，数据基础负责建立可治理的数据底座，事实来源把业务概念映射到具体实体，Skills 规定智能体如何找到并使用它们，验证层则持续发现仍然漏出的失败模式。

### 数据基础（Data foundations）

要保证分析智能体的准确性，最重要的是打好数据基础。这包括数据仓库中的数据模型、转换逻辑、测试和表，以及描述它们的元数据。维度建模、测试左移、关键数据管道的新鲜度和完整性检查等标准数据工程与数据质量实践依然适用，而且和过去一样重要。

“上个月有多少活跃用户？”这个问题的事件记录位于一张事实表中，但“活跃”的具体定义，取决于查询锚定了哪些维度：注册、登录、发生事件，还是付费。

```text
┌─ FCT_USER_ACTIVITY（用户活动事实表）
│
├── user_id (FK) ──────────────> DIM_USERS.user_id
│                                  └─ 口径：注册用户
│
├── date_id (FK) ──────────────> DIM_DATES.date_id
│                                  └─ 口径：指定日期内活跃
│
├── session_id (FK) ───────────> DIM_SESSIONS.session_id
│                                  └─ 口径：发生登录会话
│
└── subscription_id (FK) ──────> DIM_SUBSCRIPTIONS.subscription_id
                                   └─ 口径：有效付费订阅
```

| 数据表 | 主键/外键 | 其他主要字段 |
| --- | --- | --- |
| `FCT_USER_ACTIVITY` | `activity_id`（PK）；`user_id`、`session_id`、`subscription_id`、`date_id`（FK） | `event_count`、`session_minutes` |
| `DIM_USERS` | `user_id`（PK） | `email`、`created_at`、`signup_source` |
| `DIM_DATES` | `date_id`（PK） | `month`、`quarter`、`year` |
| `DIM_SESSIONS` | `session_id`（PK）；`user_id`（FK） | `started_at`、`duration_sec` |
| `DIM_SUBSCRIPTIONS` | `subscription_id`（PK）；`user_id`（FK） | `plan`、`status`、`started_at` |

这正是维度建模等标准数据工程实践依然重要的原因：事实记录本身并不能消除业务定义的歧义，必须通过经过治理的维度、指标和过滤条件明确口径。

变化在于，数据模型的最终用户不再只是数据科学家等数据专家，而是代表不同用户行动的智能体；这些用户的数据专业程度和对底层基础设施的理解各不相同。由此产生的挑战是：系统不能要求最终用户亲自验证结果是否正确，因为他们通常没有这方面的知识。

数据基础层主要用来消除歧义。以“收入”为例，如果这个概念只会解析到一个经过治理的数据集，而不是四十个貌似合理的候选项，那么问题在智能体开始搜索之前就基本得到了解决。这一层也是抵御陈旧问题的第一道防线：定义规范模型的同一代码仓库，正是强制这些模型保持最新的最佳位置。

以下做法尤其有效：

- **创建规范数据集**：最常见的失败，是智能体无法把一个概念（例如“产品 X 的收入”）映射到唯一正确的表、列和指标定义，因为系统中往往存在多个实现略有差异、看起来都合理的候选项。解决方法是减少逻辑模型的数量，并加强治理：维护一小组归属明确、可直接使用、易于发现的规范单一事实来源数据集，同时积极废弃近似重复项。为了成本和性能而建设的物理汇总表与缓存仍有价值，但它们应机械地从规范模型派生，而不应作为并列的替代数据源存在。目标是让智能体搜索一个概念时，只找到一个经过治理的答案。
- **强制执行标准**：只有通过工具、CI 和组织规范共同执行，数据基础才能保持稳定。工具应在结构上优先把智能体引导到规范模型；绕过标准的改动应在 CI 审查中失败；下游团队必须基于治理层建设，否则就要说明原因。没有执行机制的治理，很快会退化回“多个候选答案”的老问题。
- **让相关资产共置（colocation）**：面对持续变化的数据模型与业务逻辑，Anthropic 的主要防线是共置。几乎所有数据代码——包括建模、语义层、参考文档和规范仪表盘定义——都放在同一个仓库中，并由 CI 检查保护跨层完整性。如果某个建模改动会破坏下游仪表盘，或使已有指标文档失效，CI 会指出问题，修复也会在同一个 PR 中提交。
- **把元数据当作一等产品**：编码智能体表现出色，部分原因是代码库具有很强的可读性，例如 README、类型签名和文档字符串。只要以和数据转换同样严格的方式维护表与列说明、规范指标定义、粒度说明、有效值范围、血缘、所有者和模型分层，数据仓库也可以同样“可读”。良好的治理会给智能体提供选择正确数据集所需的关键上下文。

### 事实来源（Sources of truth）

如果数据基础是数据仓库本身，那么事实来源就是智能体用来理解和导航仓库的参考界面。这一层负责减少概念与实体之间的歧义，把业务相关方问题中的“周活跃用户”转化为数据模型里一个具体、受治理的实体。

Anthropic 使用的事实来源，按可信度大致从高到低排列如下：

- **语义层**：包含编译后的指标和维度定义。只要问题能够清晰映射到一个已定义指标，智能体就调用函数并得到一个数字；这个数字与公司其他入口产出的结果完全一致。Anthropic 通过 Skill 指令，在结构上强制智能体优先使用语义层。团队曾尝试让 LLM 根据原始表和查询日志自动生成指标定义，以此快速搭建语义层，但这个方案没有奏效：它生成的定义看似合理，实际上却把原本要消除的歧义编码了进去。与规模更小、由人工整理的语义层相比，自动生成方案反而降低了评测表现。因此，Anthropic 建议用 Claude 生成文档，但由人类负责指标定义。
- **数据血缘与转换图**：当语义层无法覆盖问题时，数据血缘和基于引用次数的表排名，可以帮助智能体判断哪些上游模型支撑某个概念、哪些已经废弃、哪些具有相同粒度。这样，“我不知道这个指标”就转变为“我知道应该从哪个治理模型聚合”。数据血缘也是后文在线验证所需新鲜度和来源信号的基础。
- **查询语料库**：来自仪表盘、Notebook 和历史分析的 SQL。直觉上，它应该很有价值，因为它记录了已经被正确回答过的问题。但实践中，让智能体直接检索数千条历史查询，准确率提升不到 1 个百分点。非结构化检索无法稳定地把新问题映射到正确先例。真正有效的方法，是把查询语料提炼为按领域组织的结构化参考文档，以及 Skill 中的可复用分析模式。因此，应把查询历史视为内容整理的原材料，而不是让智能体直接阅读的事实来源。
- **业务上下文**：这是最容易被团队忽略、也是 Anthropic 很长时间里低估的一层。不了解业务的智能体可能会回答用户字面上提出的问题，却无法理解用户真正想问什么。它不知道“第二季度发布”指的是哪个具体产品，也不知道两个团队对同一个词有不同定义，更不会意识到用户之所以提问，是因为周四要召开董事会。Anthropic 接入了由索引文档、路线图、决策记录和组织结构构成的公司知识图谱，使智能体能够解析隐含指代，并提出更好的澄清问题。

四类事实来源面对的共同失败模式，与数据基础层相同：**文档质量差或已经过期。** Claude 很适合帮助缩小缺口，例如起草列说明、根据查询模式提出指标文档草稿、在 CI 中标记缺少文档的模型，但最终的整理工作和所有权仍由人负责。

### Skills

如果事实来源是智能体的**声明式知识**——例如某个指标是什么意思——那么 Skill 就是它的**程序性知识**：应该按什么顺序查询哪些来源，如何处理有歧义的数据，以及一份完成的分析应该是什么样子。

在 Claude Code 中，Skill 是一个由 Markdown 文件组成、可由智能体按需读取的文件夹。Anthropic 开发的 Skills 带来了巨大的增益：没有 Skills 时，Claude 在内部评测中回答分析问题的准确率不超过 21%；加入 Skills 后，整体准确率可以稳定超过 95%，某些领域经常达到约 99%。本文附录提供了 Anthropic 常用 Skill 的骨架。

#### 创建成对的 Skills

Anthropic 通常把 Skills 成对设计：

- **知识 Skill（knowledge skill）**是一个轻量的顶层路由器，让领域细节可以按需加载。它会规定：“先尝试语义层；如果语义层没有覆盖，则查看这个领域约 30 个参考文件，其中记录了相关表、字段、连接方式和注意事项。”这正是对检索失败的回应：它不会让智能体直接搜索拥有数百万字段的数据仓库，而是在写查询之前，先把范围缩小到几十个经过整理的文件。
- **操作手册 Skill（runbook skill）**编码了一位资深分析师会遵循的流程：澄清问题，通过知识 Skill 找到来源，执行查询，再让对抗性审查子智能体反复检查结果。它还会打包十余种可复用的分析模式，例如留存曲线、比率分解和漏斗分析，避免每次收到常见请求都重新发明方法。

#### 创建适合 LLM 检索的参考文档

参考文档应专门为 LLM 检索而写。Anthropic 的文档会说明表的粒度、范围和排除项，解释易错细节的机制（例如“排除已知免费邮箱域名，但保留 anthropic.com 这类自定义域名”），并给出明确的路由触发条件（例如“如果问题涉及实验提升，则使用本数据；不要用于原始事件计数”）。文档不应堆砌容易过期的规定式步骤。

一个参考文档骨架如下：

```markdown
# [领域] 数据表

## 快速参考

### 业务上下文——[用通俗语言说明该领域的含义]
### 实体粒度——[一行数据代表什么]
### 标准数据清洗过滤器——[该领域每条查询都应使用的过滤条件]

## 维度

- [关键维度的编码方式，以及同一概念在不同表中的不同命名]

## 关键表

### [table_name]

- **粒度**：[...] · **范围/排除项**：[...]
- **用法**：[何时使用、何时不要使用、连接键、必需过滤条件]

[...每个受治理的数据表对应一个简短小节...]

## 易错点

- [资深分析师会特别提醒的错误答案模式]

## 最佳实践/常见查询模式

- [默认选择、标准切分方式，以及难点主要在查询形式时的完整模式]

## 交叉引用

- [负责相邻问题的其他领域文档]
```

#### 把 Skill 维护当作一等任务

Skill 文档描述的是每天都在变化的数据模型；如果不主动维护，几周内就会出错。Anthropic 曾看到离线准确率从上线时约 95% 漂移到一个月后的约 65%，此后才真正把 Skill 维护当作工程问题。

具体做法是把 Skill 的 Markdown 文件与转换模型放在同一个仓库中，因此修改模型的 PR 也必须同时更新描述模型的文档。代码审查钩子会标记任何修改了报表模型却没有修改 Skill 文件的提交。如今，大约 90% 的数据模型 PR 都会在同一个 diff 中包含 Skill 改动。随着模型改善、旧的失败模式不再适用，团队也会定期删减 Skill 中多余的脚手架。

#### 在所有入口提供一致体验

同一个 Skill 必须在 Slack、IDE、仪表盘工具和独立智能体会话中，对相同问题给出相同答案。Anthropic 通过一个规范来源——数据仓库——以及自动同步机制实现这一点。代码合并后，Skill 会同步到面向 IDE 用户的插件市场、供托管应用读取的云存储对象，并通过 MCP 直接作为资源提供。

团队从一开始就考虑可移植性，避免硬编码仓库路径或只属于某个入口的命名空间。

### 验证（Validation）

验证的目的，是找出三类失败模式中还有哪一种正在从系统中泄漏出来。

#### 离线评测

一个常见问题是，数据团队搭建了非常复杂的分析环境，却没有任何流程来了解分析智能体究竟有多准确。

离线评测可以弥补这一缺口。它由简单的问题/答案对组成，类似机器学习模型的离线测试：它不能直接说明线上智能体的实际表现，但可以很好地揭示系统是否存在关键缺口。

Anthropic 使用两类离线评测：

- **基于仪表盘的评测**由 Claude 自动生成，再经人工验证，覆盖业务相关方最常提出的问题。
- **长尾评测**把路线图、表文档等业务上下文提供给 Claude，让它针对领域内其他内容生成合理问题。

此外，只要业务相关方在讨论中纠正了智能体，这次纠正就会被持续收集，成为候选评测用例。

其他最佳实践包括：

- **锚定事实，避免基准漂移**：针对实时数据编写的评测，会在底层数字变化时立即过期。应把评测固定到某个快照日期，基于稳定事实表编写，或让评分器评估智能体的查询而不是最终数字。把评测套件接入 CI，让修改依赖项的 PR 自动重跑受影响的评测。
- **像存遥测数据一样保存结果，而不是像存测试日志一样**：每次运行都写入数据仓库表，记录 Skill 版本、Git SHA、模型 ID、每条断言的通过/失败、Token 数量和耗时。“这次改动有没有帮助？”因此会变成一个可查询的问题，同时也能得到时间序列，用来发现单次 CI 无法捕获的缓慢退化。
- **按领域设置上线门槛**：在某个领域对应的评测集达到阈值之前，领域负责人不能向业务用户发布智能体。Anthropic 最初采用约 90% 的门槛，这会迫使团队在用户看到错误之前先修复参考文档。
- **选择合适的评测数量**：数量取决于业务领域和底层数据模型的复杂度。可以通过跟踪离线准确率对线上准确率的预测能力来校准。Anthropic 发现，每个主题（例如“增长”）超过几十条后，边际收益就会递减；而且随着新一代模型出现，达到收益上限所需的数量还会下降。
- **离线评测准确率应接近 100%**：每个正确答案还应命中语义层（如果已有语义层）。即使达到这一水平，也不能证明系统绝不会给出错误答案；它只说明，在评测覆盖合理的前提下，系统不存在明显缺口。

#### 消融方法

Anthropic 在决定 Skill 的结构时——例如暴露哪些来源、一个子智能体是否值得增加延迟、两个 Skills 是否应该合并——会始终固定离线评测集，只改变一个组件并比较通过率。每次运行只需约一小时，却能替代大量争论。方法本身比任何单次结果更重要。

- **为“没有效果”的结果做设计**：Anthropic 最有价值的一次消融实验，恰恰得到了负面结果。团队让智能体可以直接 `grep` 整个仪表盘、数据转换和分析师 Notebook 的 SQL，共计数千个文件，并通过会话记录确认它在每次回答前确实读取了这些文件。结果准确率在正负方向上的变化都不到 1 个百分点。对于答错的问题，约 80% 的情况下，正确答案实际上就存在于语料库中；但“答案存在”并不能预测智能体会改为答对。信息在那里，智能体看到了，却仍没有正确使用。这说明瓶颈不在能否访问历史工作，而在信息结构，也就是能否把问题映射到正确实体。这个结论改变了团队此后数月的路线图。
- **以 PR 为粒度做消融**：每次有意义的 Skill 修改，都应在相关评测切片上运行修改前/后的对比，并把差异写进 PR 描述。这能真实检验“我改进了文档”的说法，也能发现那些出于好意却反而使结果变差的改动。
- **保留一份精简的失败清单**：Anthropic 的两个例子是：超过某个点后继续叠加文档优化轮次，连续三次产生负收益，因为文档只是变得更长而不是更好；为了降低延迟而把对抗性审查换成更便宜的模型，则丢失了大部分准确率收益，却没有获得真正的速度提升。记录负面结果成本很低，却能防止后来者重复同样的实验。

#### 在线验证

最后一步，是尽可能保证线上系统的实际表现。Anthropic 采用了以下措施：

- **对抗性审查**：使用一个 Claude Skill 主动挑战候选答案的所有底层假设，在内部评测集上把准确率提高了 6%，代价是 Token 消耗增加 32%，延迟提高 72%。
- **来源页脚**：每个回答都附带页脚，说明答案来自哪个层级（语义层 > 整理后的参考资料 > 原始表）、底层数据有多新，以及模型归谁负责。它不会直接让答案更正确，但可以帮助使用者判断可信度。“原始表，新鲜度未知”意味着在向上汇报前应再次核验，也是对静默失败为数不多的缓解措施之一。
- **数据质量检查**：智能体可能使用了正确字段和正确方法，但数据本身是错的。因此，应进行基础质量检查，确保所引用字段足够新、足够完整且不存在异常。
- **被动监控**：Anthropic 持续跟踪两个线上信号：通过语义层解决的智能体查询比例，以及回答中出现纠正性语言（如“用错表了”“漏掉了欺诈过滤条件”）的比例。它们进入一个每周审查的仪表盘，并与离线通过率一起分析。
- **主动收集纠正信息**：这是闭环的关键。一个定时智能体每隔几小时扫描业务沟通频道中的纠正性语言，针对相关参考文档起草一行修复，并创建一个指派给领域负责人的 PR。修复路径被刻意设计得非常简单：编辑 Markdown、合并、自动同步到所有入口。因此领域负责人不需要花费太多时间，而同一条纠正也会进入离线评测集。

这些方法仍无法完全捕获一种失败：**静默失败**。答案是错的，却看起来合理，并且在没有人提出异议的情况下被使用。Anthropic 的缓解措施包括来源页脚、对任何要提交给管理层的内容进行明确人工签字，以及为每个领域的核心 KPI 设置常驻评测，每天与官方仪表盘进行合理性核验。但团队坦言，目前还没有强健的彻底解决方案。

## 如何开始

如果从零开始，只需要少量规范数据集、几十条离线评测和一个轻量的知识 Skill，就能获得大部分收益。本文其余机制，都是 Anthropic 在这些基础能力就位后逐渐补充的。

并非所有最佳实践都适合每一个数据团队。在选择方法之前，应先围绕以下原则在组织内达成共识：

- **今天得到正确答案与未来得到正确答案，哪个更重要？** AI 模型进步很快。很多公司会针对当前模型的不足建设大量基础设施，但模型改进后，这些设施可能失去意义。理解模型短板并等待后续模型填补缺口，运营开销会低很多，但未必符合每家公司的风险承受能力。
- **预计业务复杂度会如何变化？** 如果公司数据不多、结果使用者很少，或数据模型预计会一直比较简单，那么本文的一些流程可能属于过度建设。
- **目标读者的技术水平如何？** 如果系统服务的是能够识别错误答案的数据科学家，团队可以比“面向完全不了解底层数据模型的用户”容忍更多错误。
- **愿意为提升准确率付出多少成本？** 对抗性验证等流程可以显著提高准确率，但通常也会增加成本和延迟。
- **对访问控制和内部数据隐私的容忍度如何？** 智能体掌握的上下文越多，表现通常越好；但广泛的数据访问权限又与大多数公司的治理立场相冲突。这个选择会决定团队应该构建一个通用智能体，还是多个权限受限、范围明确的智能体。

无论选择哪条路线，Anthropic 最大的收益都来自对三类失败模式的直接治理：把歧义收敛为一个受治理的答案，让这个答案容易被发现，并在答案或其发现机制变得陈旧时及时发出警报。
